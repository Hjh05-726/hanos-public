# Knowledge types

Route durable material to existing authorities. Do not create a new top-level category merely because the request uses a new label.

| User need | Handling |
|---|---|
| Long-term information or work preferences | Update an existing global authority; otherwise capture minimally for classification, excluding sensitive details |
| Project knowledge and current state | Use that project's existing index or overview; separate current evidence, hypotheses, and history |
| Goal management | Use the existing active or completed goal area and its template |
| Decision record | Record options, choice, reason, cost, and reopening condition in the existing decision authority |
| User correction | Correct the authoritative node, identify the superseded statement, and preserve an auditable history |
| Methodology | Capture a clear, low-risk method with its source project; ask before promoting an uncertain or cross-project generalization |
| Agent result or conversation | Extract durable facts, decisions, corrections, methods, or open questions; do not store raw conversation by default |
| Archive or deletion | Require explicit intent and follow local governance |
| Search, handoff, or task context | Generate from targeted reads; save the generated result only when explicitly requested, following the [read protocol](read-protocol.md) |
| Duplicate, conflict, or expiry audit | Report findings first; merge, supersede, archive, or delete only on explicit request |

When one input contains several types, classify each durable item separately. Do not use a catch-all note as a parallel database.

A separate, clear, low-risk new knowledge item in the same user message may
still follow the ordinary [write protocol](write-protocol.md) for automatic
capture. Its presence does not authorize saving the generated handoff or task
context.
